# Milvus 3.0 branch — design

**Date:** 2026-09-03
**Branch:** `milvus-3.0` (long-lived showcase branch, not merged to `main`)
**Status:** Draft, awaiting review

## Goal

A variant of the e-commerce search demo that runs against a **Milvus 3.0-compatible Zilliz
Cloud instance** and makes the 3.0 features already presented in `~/Projects/milvus_es_lab`
visible in an e-commerce UI. Where the lab showed a feature as a code panel next to an
Elasticsearch equivalent, this branch shows the same feature doing an everyday shop-search job:
highlighted matches, live facet counts, exact-phrase search, "one per brand", "boost cheaper",
"new arrivals", "ships from near me".

The narrative for the branch mirrors the lab's: **3.0 removes the workarounds.** Two hacks in
the current app go away outright — the client-side over-fetch-and-sort (`POOL_SIZE`) and the
build-time `facets.json`.

## Why this shape

- **Preview environment of the existing Pages project** (`milvus-3-0.vdb-ecom.pages.dev`). The
  branch keeps the `ZILLIZ_ENDPOINT` / `ZILLIZ_TOKEN` names; the preview-environment secrets are
  set to the 3.0 instance (`wrangler pages secret put ... --environment preview`). Trade-off
  accepted: other preview branches will also hit the 3.0 instance while those secrets are set.
- **Tokens.** The app keeps the read-only `ZILLIZ_TOKEN`; the loader uses `ZILLIZ_WRITE_TOKEN` (data admin) from `.dev.vars` only. Verified 2026-09-03: the read key is denied `CreateCollection`, the write key can create/drop. The target is a dedicated 3.0 cluster (aws-eu-west-1) that already holds an unrelated `amazon_reviews` collection, which the branch never touches.
- **Lab parquet as source.** `simonhearne/milvus-es-live-data` on Hugging Face: 97,894 rows,
  12 columns, `text_vec` + `image_vec` already embedded (1024-d, produced by the same ingest
  pipeline as this app's notebook — Qwen3-Embedding-0.6B text, SigLIP image). A pymilvus 3.x
  loader creates the 3.0 schema and inserts; no re-embedding. Query-embedding parity with
  Workers AI is verified in STEP 0 before anything else is built.
- **Replace, don't toggle.** No "3.0 mode" switch. The branch *is* the 3.0 app; the diagnostics
  panel's pymilvus rendering is how the audience sees what changed.
- **REST v2 stays the transport.** Pages Functions cannot use gRPC/pymilvus, so every feature
  must be reachable through Zilliz REST v2 on the 3.0 instance. Which parameters exist, and under
  what names, is the single biggest unknown — hence STEP 0 below.

## Collection: `amazon_reviews_v3`

Created by `scripts/load_v3.py` (pymilvus ≥ 3.0, pyarrow). Never created by hand.

Analyzers (same chain as the lab, so the lab's parity numbers carry over):

```python
EN_ANALYZER  = {"tokenizer": "standard",
                "filter": ["lowercase", "asciifolding",
                           {"type": "stemmer", "language": "english"},
                           {"type": "stop", "stop_words": ["_english_"]}]}
SYN_ANALYZER = same, with {"type": "synonym", "synonyms": <rules>, "expand": True}
               inserted immediately before the stemmer
```

Synonym rules are copied from the lab's `data/synonyms.txt` into `scripts/synonyms.txt`
(equivalence groups: ipad/tablet, laptop/notebook, tv/television, earbuds/earphones/headphones,
mic/microphone, cord/cable, plus the misspelling groups).

Indexes:

```
text_vec, image_vec        IVF_RABITQ (nlist 1024, refine SQ8) → fallback AUTOINDEX; COSINE
text_sparse, text_syn_sparse   SPARSE_INVERTED_INDEX → fallback AUTOINDEX; BM25
main_category, store, price, average_rating, rating_number   INVERTED
store_location             RTREE (only index GEOMETRY accepts)
first_seen                 none (TIMESTAMPTZ accepts no index)
```

Synthetic columns follow the lab's `data/synthesize.py` exactly (sha256-seeded, so reloads are
deterministic): `store_city`/`store_location` from a fixed 40-city list keyed by `store`;
`first_seen` spread over the trailing 730 days with 20% inside the last 30 days, anchored to load
time. **Trap carried over:** "Listed within 30 days" returns nothing if the collection is reloaded
more than 30 days before the demo. Re-run the loader (or just its `--reanchor` mode, which
re-upserts `first_seen` only) before a talk.

Loader hygiene from the lab: batches of 500, explicit `flush`, compaction, then
`load_collection`. `--drop` recreates; without it the loader refuses to touch an existing
collection. Sparse fields are function outputs and are never inserted.

Data facts from the parquet that change existing app assumptions: **no `-1` price sentinels**
(min 0.0099) and no nulls. `hasPrice()` and the `price > 0` clause are kept (harmless) so the
code diff stays focused.

## Design

### 1. Shared contract (`src/lib/types.ts`)

```ts
interface Filters {              // existing fields unchanged, plus:
  phrase?: string | null;        // exact phrase → PHRASE_MATCH(text_snippet, phrase, 2)
  listedWithinDays?: number | null;   // 30 | 90 | 365 → first_seen > ISO '<cutoff>'
  near?: { city: string; km: number } | null;  // → st_dwithin(store_location, 'POINT (lon lat)', km*1000)
}
type SortKey = ... | "newest";   // order_by first_seen desc
type Boost = "cheaper" | "rated" | "popular" | "newest";
type Fusion = "weighted" | "rrf";
interface SearchRequest {        // existing, plus:
  fusion?: Fusion;               // default "weighted" (α applies only to weighted)
  synonyms?: boolean;            // default true → sparse field text_syn_sparse, else text_sparse
  groupByBrand?: boolean;        // → groupingField:"store", groupSize:1
  boost?: Boost | null;          // → decay reranker
}
interface Product {              // existing, plus:
  first_seen?: string;           // RFC3339
  store_city?: string;
  highlight?: string;            // snippet fragment with sentinel-marked matches (see §5)
}
interface SearchDebug {          // existing, plus:
  orderBy?: { field: string; order: "asc" | "desc" }[];
  groupBy?: string;
  ranker?: string;               // "WeightedRanker(0.6,0.4)", "RRFRanker(60)", "FunctionScore(decay price gauss …)"
  highlighter?: boolean;
  sparseField?: "text_sparse" | "text_syn_sparse";
  tokens?: string[];             // run_analyzer output for the cleaned query (probe 11)
  indexType?: string;            // from indexes/describe, fetched once per isolate (probe 12)
}
interface FacetsResponse {       // new endpoint
  categories: { value: string; count: number }[];
  brands: { value: string; count: number }[];
  priceMin: number; priceMax: number;
  total: number;                 // count(*) under the current filter
  debug: { filter: string; pymilvusQuery: string; zillizMs: number };
}
```

`Facets` (static) and `public/facets.json` are deleted along with `scripts/build-facets.mjs`
and the `build:facets` npm script. The city list for `near` lives in `src/lib/cities.ts`
(name, lon, lat) and is the same list the loader uses.

### 2. Sorting — `order_by_fields` replaces the pool sort

`applySort`, `POOL_SIZE`, the `pool` debug field, and the "N+" truncated-pool UI are removed.
Every branch passes the page's real `limit`/`offset` plus:

```
sort=price_asc  → orderByFields:[{field:"price",order:"asc"}]
sort=price_desc → [{field:"price",order:"desc"}]
sort=rating     → [{field:"average_rating",order:"desc"},{field:"rating_number",order:"desc"}]
sort=reviews    → [{field:"rating_number",order:"desc"}]
sort=newest     → [{field:"first_seen",order:"desc"}]
sort=relevance  → omitted
```

Semantics recorded from probe 2 are shown in the diagnostics panel ("sorted server-side over the
top-N relevance window" vs "over the whole filtered set") so the demo is honest about what the
kernel sorts. `total` is no longer reported for sorted pages; pagination shows page numbers
only, as it already does for relevance.

### 3. Facets — live aggregation endpoint

New Pages Function `functions/api/facets.ts`, `POST /api/facets` with body
`{ q?: string; filters?: Filters }`. Runs three `entities/query` calls in parallel:

1. categories: `groupByFields:["main_category"]`, `outputFields:["main_category","count(*)"]`,
   ordered by `count(*)` desc, `limit 60`, under the compiled filter **minus** the category clause;
2. brands: same on `store`, `limit 40`, under the filter minus the brand clause;
3. bounds: `outputFields:["count(*)","min(price)","max(price)"]` under the full filter.

When a query is committed, the facet filter also includes `TEXT_MATCH(text_snippet, "<cleaned
query>")` so counts are scoped to products that lexically match the query (aggregations run over
`query`, not vector search, so this is the closest query-aware count the engine offers). The rail
labels the counts "in catalogue matching your search".

The client (`App.tsx`) calls `/api/facets` alongside `/api/search` whenever the committed query
or filters change (not on page/sort/α changes). `FilterPanel` renders counts next to each brand
and category, and the price slider bounds come from the response. The same edge-cache pattern as
`/api/search` applies (key = hash of `{q, filters}`, 1-day TTL). A facets failure never blocks
search: the rail falls back to whatever it last had.

### 4. Search branch changes (`functions/api/search.ts`)

Dispatch order is unchanged (similar → search → browse). Within **search**:

- **Sparse field** = `text_syn_sparse` when `synonyms !== false`, else `text_sparse`.
- **Fusion**: `fusion === "rrf"` → `rerank:{strategy:"rrf",params:{k:60}}` and α ignored; else the
  existing weighted path. α=0/1 extremes still short-circuit to single-field search.
- **Group by brand**: `groupingField:"store"`, `groupSize:1` on the search/hybrid request
  (`strictGroupSize:true`). Disabled in the UI wherever probe 6 says it is unsupported.
- **Boost** (decay reranker, `FunctionScore`), parameters chosen to read like the lab's:

  | boost | input | function | params |
  |---|---|---|---|
  | cheaper | `price` | gauss | origin 0, scale 30, offset 10, decay 0.5 |
  | rated | `average_rating` | gauss | origin 5, scale 1, offset 0.2, decay 0.5 |
  | popular | `rating_number` | exp | origin 500000, scale 100000, offset 0, decay 0.5 (probe 7 tunes) |
  | newest | `first_seen` | gauss | origin = now (day-rounded ISO), scale 30d, decay 0.5 — only if probe 7 accepts TIMESTAMPTZ |

  Stacking: if probe 7 shows the decay ranker can be applied on top of fusion in
  `hybrid_search`, boost works at any α. If not, boost is applied on the single-field paths only
  and the UI greys the boost control while α is strictly between 0 and 1, with a tooltip saying
  why. Either way the diagnostics `ranker` string shows exactly what ran.
- **Phrase**: `Filters.phrase` compiles to `PHRASE_MATCH(text_snippet, "<esc>", 2)` in
  `compileFilter` and applies to every branch and sub-search.
- **Dates**: `listedWithinDays` compiles to `first_seen > ISO '<cutoff>'` where the cutoff is
  `now − N days` rounded down to UTC midnight (so the cache key is stable within a day).
- **Geo**: `near` compiles to `st_dwithin(store_location, 'POINT (<lon> <lat>)', <km*1000>)`
  using the city table; unknown city names are rejected with a 400.
- **Highlighting**: whenever a sparse sub-search is present (α<1, or RRF), the request carries
  `highlighter` for `text_snippet` with sentinel tags `\u0001` / `\u0002` (never `<em>`, so escaping is unambiguous), `fragmentSize 160`,
  `numOfFragments 1`. `toProduct` copies the first fragment into `Product.highlight`.
- **Output fields** gain `first_seen`, `store_city`.
- `pymilvusQuery` builders gain `order_by_fields`, `group_by_field`/`group_size`, `ranker`
  (`RRFRanker`, `WeightedRanker`, `FunctionScore(functions=[Function(...)])`) and `highlighter`
  (`LexicalHighlighter(...)`) so the panel stays a faithful pymilvus 3.x transcript.
- **Cache key** normalisation adds `fusion`, `synonyms`, `groupByBrand`, `boost`, and the three
  new filter fields (with the date cutoff, not the day count, so day rollover misses cleanly).

Query understanding: before the LLM call, a deterministic pass extracts `"quoted phrases"` into
`Filters.phrase` and removes them from the text the model sees; the cleaned query for embedding
and BM25 keeps the phrase words (they are still relevant terms). The LLM prompt and schema are
unchanged in this branch (date/geo phrases in natural language are a possible follow-up, not in
scope).

### 5. UI (`src/components`, `src/App.tsx`)

- **ProductCard**: renders `highlight` when present. The fragment is HTML-escaped first, then the
  two sentinels become `<mark>` / `</mark>` — so nothing from the DB is ever injected as markup.
  Shows a **New** badge when `first_seen` is within 30 days and a "Ships from {store_city}" line.
- **Header**: Sort gains **Newest**. Beside the blend slider: **Fusion** segmented control
  (Weighted / RRF; α slider disabled under RRF), **Synonyms** toggle, **One per brand** toggle,
  **Boost** select. All four are search-mode only (hidden in browse/similar), like the slider, and
  live in the filter drawer on mobile.
- **FilterPanel**: brand and category lists show counts from `/api/facets`; new **Listed within**
  (Any / 30 days / 90 days / 1 year) and **Ships from** (city select + 250 / 1000 / 5000 km)
  groups. Price slider bounds come from the facets response.
- **InterpretationNote**: shows an "exact phrase: …" chip when a quoted phrase was extracted.
- **Empty state**: a "Try:" row of example chips that exercise the branch — `"noise cancelling"
  headphones`, `tablet under $200` (synonyms → iPads), `laptp charjer` (typo absorbed by dense +
  synonym rules), `usb-c hub 4 stars`.
- **DiagnosticsPanel**: new rows for order-by, group-by, ranker, sparse field, highlighter, tokens,
  index type, and a facets sub-section (filter + pymilvus aggregation call + latency). The
  "pool/N+" row is removed.

All new request fields persist across queries like α does (global preferences); a new query text
still clears the filter rail (existing behaviour), which now also clears `phrase`, `near`, and
`listedWithinDays`.

## Error handling

- Every new proxy feature degrades rather than fails: missing highlight → plain snippet; facets
  error → rail keeps last counts and search still runs; decay/group unsupported in a given branch
  → control disabled with a reason, request sent without it.
- Zilliz errors from unknown parameters surface verbatim in the 502 body (as today) so a
  regression on the instance is visible in the diagnostics panel rather than silently absorbed.
- The loader is the only writer; the app's token stays read-only (Search/Query/Describe).

## Testing

- `scripts/probe-v3.mjs` PASS on every row it can (its table is the acceptance record).
- `npm run typecheck` clean.
- Manual, via `npm run dev` on `:5173`: each UI control changes the diagnostics `pymilvusQuery`
  as expected; sort by price no longer shows "N+"; facet counts change when a brand is toggled;

  yields distinct `store` values on the page; boost "cheaper" moves low-price items up without

- Preview deploy at `milvus-3-0.vdb-ecom.pages.dev` after preview-environment secrets are set.

## Out of scope

Multilingual analyzer, model rerankers, SemanticHighlighter, embedding functions, NL
understanding of date/geo phrases, any change to the `main` branch or to the 2.x collection.

## Verified facts (live, 2026-09-03)

Recorded by `npm run probe:v3` against `amazon_reviews_v3` on the dedicated Milvus 3.0
cluster, read-only token. Encoded in `functions/api/rest.ts` (`REST_NAMES` / `CAPS`) — that
file, not this table, is what the proxy imports.

**Method.** The REST v2 request decoder is *strict about types on fields it knows* and
*silently drops fields it does not know*. A call that returns HTTP 200 therefore proves
nothing on its own. Every row below is either an observable effect (the order changed, the
score changed, the rows are distinct) or a deliberate type-mismatch probe: sending a
wrong-typed value for a field that exists yields `Mismatch type ...`, while a field that is
absent from the struct swallows it silently. Rows marked `WEAK` are exactly that trap — the
call succeeded and the parameter did nothing.

### Exact shapes the proxy must emit

- **order_by (probe 2)** — `entities/query` only, `orderByFields: ["price"]`. The value is a
  plain `string[]` of *field names*: `[{field, order}]` is rejected with a type mismatch and
  `["price asc"]` with `order_by field 'price asc' does not exist in collection schema`.
  Ascending only — no direction field exists (`orderByType` / `orderByDirection` /
  `descending` / `desc` / `reverse` / `sortOrder` are all absent from the struct). Multiple
  fields work as a lexicographic sort. `first_seen` is rejected: *"has type Timestamptz which
  is not sortable"*.
- **Aggregation (probe 3)** — aggregate expressions go in `outputFields` on `entities/query`:
  `["count(*)"]`, or any mix of `min()/max()/avg()/sum()`. One row comes back, keyed by the
  literal expression (`{"min(price)": 0.01, "max(price)": 12999}`). `count(*)` **cannot** be
  combined with the others (*"count entities with pagination is not allowed"*) and cannot be
  combined with a plain column (*"output_fields can only contain aggregation expressions"*).
  Any filter, `TEXT_MATCH` included, applies.
- **Decay / boost (probe 7)** — `functionScore: { functions: [{ name, type: "Rerank",
  inputFieldNames: ["price"], params: { reranker: "decay", function: "gauss"|"exp"|"linear",
  origin, scale, offset, decay } }] }`. `type` must be exactly `"Rerank"`. Accepted
  `params.reranker` values on this build: `weighted`, `rrf`, `decay`, `model`, `boost`.
  `boost` takes `{reranker:"boost", weight, filter}` and multiplies matching hits' scores.
  The `reranker` enum is not enumerated by the server, so the probe establishes it name by
  name (`unsupported reranker <x>` = unknown, any other error = known, `__bogus__` as the
  control); the `function` enum comes straight from the server's `must be one of [gauss, exp,
  linear]`.
- **Index type (probe 12)** — `indexes/describe` returns `indexType` (`"IVF_RABITQ"`) and
  `metricType` (`"COSINE"`) at the top level of the row, plus the same values as
  `indexParams: [{key,value}]` pairs.
- **Caps** — `limit` up to **16384** is accepted (the serverless `≤ 1024` cap does not apply
  here) and `limit + offset ≤ 16384` still holds. Per the plan the code keeps its clamps.

### FAIL rows and the fallback taken

- **Probe 2 — `order_by` on `entities/search` / `entities/hybrid_search`: FAIL.** The field is
  silently dropped (a bogus field name is accepted on search but rejected on query). Fallback
  per the STEP 0 table: keep the existing over-fetch → `applySort()` → slice path for search
  and similar modes, and use native `orderByFields` for browse (`entities/query`) only.
- **Probe 2 — descending order: FAIL.** No direction parameter exists. Fallback: browse sorts
  that need descending (price-high, rating, newest) stay on `applySort()`; only ascending
  sorts can use the native path.
- **Probe 3 — GROUP BY: FAIL.** No grouping parameter exists on `entities/query`; every
  candidate name is silently dropped. Fallback per the STEP 0 table: facets stay static
  (`public/facets.json`); no live per-brand / per-category counts. Scalar aggregation over the
  *whole* filtered set (`count(*)`, `min/max/avg/sum`) does work and is used in diagnostics.
- **Probe 3 — `count(*)` alongside `min()`/`max()`: FAIL.** Fallback: issue two
  `entities/query` calls when both a total and a range are wanted.
- **Probe 4 — highlighter: FAIL on both sparse and hybrid search.** There is no highlighter
  field on the REST v2 search request at all (`highlighter` / `highlight` / `highlights` /
  `highlighting` / `highlightFields` / `highlighterParams` all swallow a wrong-typed value;
  `outputFields: ["highlight(text_snippet)"]` is rejected as a missing field). Fallback per
  the STEP 0 table: no highlight; the card shows the plain `text_snippet`. Task 5 needs no
  response-shape handling — no highlight block is returned anywhere on a hit row (hit rows are
  flat: `{distance, <outputFields...>}`, with no `entity` nesting).
- **Probe 7 — decay stacking on `hybrid_search`: FAIL.** `functionScore` runs on
  `hybrid_search`, but it **replaces** the `rerank` fusion rather than composing with it:
  `rerank:weighted + functionScore`, `rerank:rrf + functionScore` and `functionScore` alone
  all return byte-identical results and raw (un-normalised, un-fused) sub-search scores.
  A second function in the `functions` array is rejected — *"currently only supports one
  rerank function"*. Fallback: the blend slider (α) and a decay boost are mutually exclusive
  on the hybrid path — when a boost is active either drop to a single-field search and decay
  on top of it, or express the fusion through `functionScore`'s own
  `{reranker:"weighted", weights, norm_score}` and forgo the decay.
- **Probe 7 — decay on `TIMESTAMPTZ`: FAIL.** *"decay input field first_seen must be numeric,
  got Timestamptz"*. Fallback: no "newest" boost; recency stays a **filter** (probe 8 passes),
  and any newest *sort* is client-side via `applySort()`.
- **Probe 8 — `orderByFields` on `first_seen`: FAIL** (Timestamptz not sortable). Same
  fallback: sort by recency in `applySort()`.
